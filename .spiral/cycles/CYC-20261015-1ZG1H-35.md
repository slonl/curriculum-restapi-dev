# Cycle: trustworthy integrated development verification

Branch: `spiral/CYC-20261015-1ZG1H-35-integrated-dev-verification`, created
from parent `main` at `7119fa8`. Matching branches were created from embedded
curriculum-rest-api `master` at `e6719f1` and curriculum-store `main` at
`6a10e1f`. The pre-existing Curriculum Store runtime/import artifacts are
preserved and outside the cycle's mutation scope.

Status: Active after maintainer confirmation on 2026-10-15.

## Analyze

The maintainer selected `curriculum-restapi-dev` and its pinned submodules as
the authoritative development environment so changes can be tested immediately
as an integrated stack.

The component assertions are currently healthy: REST passes 127/127 and Store
passes 84/84. Both default commands nevertheless exit unsuccessfully because
Tap supplies an implicit 100% coverage gate. Registration and Search have no
component suites. Compose configuration parses, but the repository has no
automated runtime exercise and mounts the real Store data directory. The parent
also records REST commit `9849ab1` while the checkout is at tree-identical merge
commit `e6719f1`, leaving the superproject visibly dirty.

No durable multi-cycle roadmap is confirmed. This cycle establishes the
verification foundation required by the newly selected submodule development
workflow without selecting later Metro, SimplyFlow, history, or import/export
product work.

`REQ-20261015-1ZG1H-36` records the agreed observable outcome and boundaries.
During planning the maintainer added 90% coverage as the desired target. The
current gap is too large to assume immediate attainment without displacing the
integrated goal, so the revised request requires an explicit 90% target check
and honest gap reporting while allowing cheap, meaningful improvements.

## Plan

### Goal

Provide one documented verification command in `curriculum-restapi-dev` that
gives an unambiguous result for the exact pinned development stack, including a
disposable-data Compose edit/history/restart exercise, without altering the
maintainer's working dataset or pre-existing artifacts.

### Likely work

1. Align the parent REST gitlink with current `master`.
2. Separate behavioral test success from explicit coverage reporting in REST
   and Store.
3. Add parent orchestration for child tests, lint where meaningful, and Compose
   configuration validation.
4. Prove Compose isolation with temporary Store data, credentials, project
   identity, and ports.
5. Exercise service readiness, REST/Search reads, authenticated edit and
   polling, audit history, Store restart, and persisted readback.
6. Bound cleanup to the test Compose project and verify repository state is
   unchanged after the run.
7. Record exact verification evidence and limitations.

The likely work is a hypothesis rather than a fixed task list. The stable scope
is the goal and non-goals below.

### Evaluation basis

The cycle succeeds when one documented command runs the behavioral checks and
the isolated Compose exercise; a disposable authenticated change becomes
queryable and visible in object history after Store restart; all involved
services receive meaningful runtime coverage; an injected failure is surfaced;
the separate coverage check reports progress against 90%; and every source
checkout plus the real development data retain their starting Git state.

### Non-goals

- Broad test-suite construction solely to close the current 90% gap.
- Complete Registration or Search component suites.
- Browser/Selenium automation.
- Excel import/export verification.
- Deployment, production data, or application architecture changes.
- Machine-wide Docker cleanup.
- Deleting or normalizing the maintainer's existing Store artifacts.

### Pause and re-plan conditions

Return to discourse if isolation requires persistent-format changes or a broad
Compose redesign; credentials or commands cannot be separated from real data;
dependency installation makes the test mutate lockfiles or remain inherently
non-repeatable; or the probe exposes a functional component failure rather than
the known coverage-policy mismatch.

## Act

REST commit `68c8e8bdf47677f65a7a9b436458c9961ca19dc6` and Store
commit `ba5723e8d636d0b8e45c8a330d3ba72e24127ac0` make `npm test`
report behavioral success while retaining coverage output, and add an explicit
four-dimensional 90% target command.

Parent implementation `5e0238585b0786a668ac2cd9dcc369461665fec3`
pins those child commits, aligns the REST pin with its merge lineage, adds the
layered verification commands and documentation, and introduces a smoke-only
Compose override. The ordinary topology now supports isolated container names
and host ports and uses service-name DNS for Search; temporary data,
credentials, logs and dependency mounts exist only in the smoke override.

The smoke runner copies the tracked Store baseline, creates a matching
integrity manifest and empty command journals, starts all four services, checks
their boundaries, performs an authenticated title update, verifies audit
history, restarts Store, verifies readback, compares repository states, and
cleans only its own Compose project.

Two disposable probes failed safely and improved the test fixture: one exposed
SimplyStore's required empty command journals, and one exposed the REST
representation negotiation boundary. Neither reached the edit step or changed
repository state.

single documented `node scripts/verify.mjs` command passes REST 127/127, Store

startup-only component coverage for Registration and Search, and no browser or
Excel workflow exercise. These do not block the agreed integrated verification
outcome and remain candidate future work.

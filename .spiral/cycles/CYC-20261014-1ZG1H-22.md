# Cycle: single-object audit trail

Branch: `spiral/CYC-20261014-1ZG1H-22-object-audit-trail`, created from parent
`main` at `a156c5e`. Matching branches were created from embedded
curriculum-store `main` at `b2f55cb` and curriculum-rest-api `master` at
`3f58316`. All three branches were clean when opened on 2026-10-14.

Status: Active.

## Analyze

SimplyStore 0.12.0 supplies immutable per-object history with command author,
message and dataset-file timestamps. The integrated curriculum environment
cannot use it: the embedded store resolves 0.11.2, the REST API exposes only a
current UUID object, and the browser has no audit route.

The project has no confirmed multi-cycle roadmap. This cycle **continues** the
maintainer's explicitly selected object-version-history direction after the
upstream SimplyStore capability became available. IndexedDB and broader
frontend modernization are already owned elsewhere and remain excluded.

SRC-20261014-1ZG1H-18 retains the maintainer's object-first direction and UI
boundary. UND-20261014-1ZG1H-19 records current behavior, the evidenced gap and
material assumptions. REQ-20261014-1ZG1H-20 defines the observable vertical
outcome. DES-20261014-1ZG1H-21 defines the cross-repository implementation.

## Plan

### Goal

From a current curriculum object view, a reader can open a complete read-only
audit trail for that object and inspect every historical snapshot with the
successful command's author, timestamp and commit message.

### Work

1. Upgrade the embedded curriculum-store dependency and lockfile to published
   SimplyStore 0.12.0.
2. Add real curriculum-shaped object-history compatibility coverage, including
   restart.
3. Add the dedicated store query and REST endpoint with JSONTag preservation,
   404/error/no-cache behavior and focused tests.
4. Add the object-view link, audit route/template and browser behavior tests.
5. Run existing child suites/lint and record the child commits.
6. Update only the two application gitlinks in the parent and verify Compose.
7. Record integrated evidence and present the cycle for maintainer evaluation.

### Evaluation basis

The cycle is successful when one fixture object has a base version and multiple
command versions; the REST endpoint returns them oldest first with exact
metadata and immutable historical contents after restart; the browser reaches
and renders that trail from the object view; unknown/failure/stale-response
behavior is bounded; existing tests remain green; and the parent pins only the
verified child revisions.

### Non-goals

- The separate standalone curriculum-store checkout.
- Property diffs, historical editing, restore or rollback.
- General command audit or same-version peer browsing.
- Original command inputs or complete historical dataset switching.
- IndexedDB and general frontend modernization.
- Dataset/schema/command/import/export format changes.
- Acceptance, integration, publication or deployment.

### Pause conditions

Return to discourse if a complete object cannot be represented without changing
the existing REST object contract or persistent formats; if history needs a new
authorization model; if the historical view must reuse editing state; or if
0.12.0 breaks existing curriculum-store behavior beyond a bounded compatibility
correction.

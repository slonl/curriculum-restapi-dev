# Cycle: FO Deprecated Replacement Probe

Repository branch: `spiral/CYC-003-fo-deprecated-replacement-probe`
Branch verified: verified on 2026-08-17; branch name matches active cycle.

## Analyze

Project state / prior evaluation that makes this cycle relevant:

Cycle 2 concluded that AI assistance is conditionally promising for review
support, not automatic continuity-link creation. The maintainer accepted that
result and requested a narrower test inside FO.

Nearest important risk / uncertainty / desired movement:

The project does not yet know whether deprecated FO entities without
`replacedBy` can be matched cheaply and safely to plausible active FO
successors using data plus Git history.

Relevant human direction / feedback:

The maintainer requested finding deprecated FO entities without `replacedBy`,
finding suitable candidates, and using Git history because candidates probably
appear around the same time as deprecation.

Governing higher-level plan / direction:

No durable multi-cycle roadmap is confirmed. Cycle 2 is the immediate governing
evidence.

Current position in that plan:

This is a deliberately narrower follow-up to Cycle 2, still independent of
production integration.

## Plan

### Cycle Goal

Produce a limited, human-auditable report of candidate replacements for selected
FO deprecated entities that have no `replacedBy`, using semantic comparison and
Git history timing.

### Why Now / Why This Cycle Boundary

This is the smallest useful next probe after Cycle 2: it tests a lower-drift
case inside one dataset before considering broader cross-dataset mapping.

### Plan Continuity Decision

Continue from Cycle 2, with narrowed scope. The cycle preserves Cycle 2's
conclusion that AI should assist review rather than mutate links automatically.

### Current Starting Evidence

- `SRC-006` records the maintainer's limited-test request.
- `UND-003` records the interpretation and constraints.
- `REQ-003` defines the observable outcome.

### Evaluation Basis

The cycle can be judged if it reports:

- sampled deprecated FO entities with missing `replacedBy`;
- candidate active FO replacements where plausible;
- Git timing evidence for both deprecated entity and candidate;
- relation confidence and uncertainty;
- cases where no good candidate is found.

### Likely Work

- Inspect FO deprecated entities without `replacedBy`.
- Exclude obvious delete placeholders or malformed rows when needed.
- Select a small sample with enough text to evaluate.
- Search active FO entities for semantic candidates.
- Use Git history to find when old and candidate entities changed.
- Produce an evidence report with candidate classifications.

### Explicit Non-Goals

- No FO data mutation.
- No `replacedBy` additions.
- No whole-dataset matching.
- No maintainer-workspace implementation.

### Pause / Re-Plan Conditions

- Git history is unavailable or too noisy to provide timing evidence.
- Deprecated rows are mostly placeholders with no semantic content.
- Candidate matching requires domain knowledge not available in the data.

Material implementation decisions or deviations from the initial likely work:

- The cycle stayed read-only against FO data.
- The first pass used exact same-type title/description matching plus Git
  timing instead of broader semantic embedding or LLM matching. This was enough
  to produce reviewable candidates while making duplicate-label ambiguity
  visible.
- A broader brute-force similarity pass was treated as too noisy/slow for this
  limited cycle and was not used as evidence.
- Evaluation feedback reopened the Act step for a bounded non-exact matching
  probe. Strict Nederlands havo had no missing predecessor descendants, so the
  bounded sample was widened to the Nederlands family excluding Nederlandse
  gebarentaal.
- A reusable read-only probe script was added at
  `.spiral/tools/fo-continuity-review-queue.mjs`. It remains Cycle 3 evidence
  tooling, not production maintainer-workspace code.

Out-of-scope discoveries retained for later:

- Deprecated parent context is incomplete for some old rows, which limits
  symmetric graph comparison.
- FO contains many repeated exact texts across active contexts, so future
  tooling needs graph/set context before ranking ambiguous candidates.
- Bounded lexical matching without graph context can identify the right concept
  in the wrong programme variant.
- Git timing through `git log -S` is useful but slow enough that future
  production work would need cached history metadata.

## Evaluate

Integrated result against cycle goal:

The cycle goal is met in a stronger evidence sense: `EVD-008` reports exact
candidate matching, `EVD-009` reports bounded non-exact matching, and `EVD-010`
verifies an enhanced review-queue probe with graph context, timing, link clues,
and focused filters.

Evidence / acceptance result:

Accepted by the maintainer in `ACC-003`.

Metric or risk movement:

The risk moved from "unknown whether this is practical inside FO" to
"practical as a review queue for exact same-type/title/description matches with
history support; non-exact matching improves recall but requires graph context;
enhanced deterministic ranking can produce a usable review queue; still unsafe
as automatic mutation."

What changed in our understanding:

- FO has a substantial missing-replacement pool (`1,453` rows), but only a much
  smaller exact-text review queue after excluding generic labels (`186` groups,
  `58` with exactly one active candidate).
- Git history is very useful when an old ID moves from active data to
  deprecated data in the same commit where a candidate ID appears.
- Strict Nederlands havo has no missing-replacement descendants in its recorded
  predecessor subgraph, so it is not a useful old-side sample for this question.
- The wider Nederlands family has `94` usable missing-replacement descendants,
  enough to test non-exact matching while remaining bounded.
- A focused `fo_doelzin`/`fo_subdomein` queue excluding generic rows leaves `15`
  old rows and `13` candidate items, which is small enough for human review.

Surprises / model mismatches:

- Exact text matching produced many duplicate candidate pairs (`1,084` pairs
  from `186` groups), so text equality alone overstates candidate certainty.
- Some strong candidates already have `replaces` links to other old IDs, which
  makes missing links plausible but not automatically certain.
- Non-exact lexical matching found plausible typo cleanup and wording-change
  candidates, but the Git timing was weaker than same-commit exact matches.
- Graph context correctly flags at least one misleading high-text-score
  subdomein candidate as a programme/level mismatch.

Known compromises:

- The probe sampled Git history instead of validating all 58 single-candidate
  groups.
- The probe did not attempt renamed, split, merged, broadened, narrowed, or
  reparented successors.
- Turtle parser validation was not run because no RDF/Turtle parser binary,
  `rdflib`, or local `n3` package was available in the environment.
- The non-exact probe used lexical scoring only; it did not use embeddings or a
  trained semantic model.
- The enhanced script is heuristic and uncalibrated; scores are ranking aids,
  not probabilities.

Unresolved issues within current goal:

No unresolved issue blocks the Cycle 3 goal. Actual FO link changes remain
outside this cycle and would require expert/domain review per candidate.

Candidate next-cycle inputs:

- Validate a few accepted/rejected candidates with a domain reviewer before any
  dataset mutation workflow is designed.
- If continuing this direction, make graph context, programme/level, existing
  `replaces`, and Git timing explicit ranking/explanation fields before trying
  broader semantic matching.
- If this becomes product work later, cache Git history metadata; live
  `git log -S` enrichment is useful but too slow for broad interactive use.

Human evaluation / feedback:

- The maintainer requested a follow-up bounded non-exact matching probe.
- The maintainer accepted the combined result: AI can help fix missing
  `replacedBy` issues faster for high-likelihood matches, but still requires
  close expert participation. This is a possible future direction, not a clear
  winner to prioritize now.

Cycle accepted, still open, or deliberately re-planned:

Accepted and closed.

## Process Learning

What context/constraint/evaluation helped:

- Preserving "review assistance, not automatic mutation" kept the conclusion
  useful without overstating the evidence.
- Checking strict Nederlands havo before widening the sample prevented the
  bounded test from pretending there were missing havo cases.
- Adding graph context exposed programme/level mismatches that text matching
  alone would have made look stronger.

What bookkeeping was useless:

No specific useless bookkeeping identified.

What should the environment learn from this cycle:

- Semantic continuity assistance should be treated as expert-led acceleration.
  A future feature should prioritize review ergonomics, explanation, and
  high-likelihood queues rather than automatic link creation.

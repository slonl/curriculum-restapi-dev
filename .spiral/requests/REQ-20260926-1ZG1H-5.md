# Stop Docker services cleanly

Maintainer report and instruction, 2026-09-26. After testing SimplyStore 0.11.1
in `curriculum-store`, the store lock remained after shutdown. The maintainer:
"I pressed ctrl-c once in the docker compose process, which should have started
normal shutdown", with no queries in flight. After the investigation below the
maintainer instructed: "Please make those changes".

Evidence from Docker's event log for that run: every service received SIGTERM
and was killed with SIGKILL exactly 10 s later (exit 137). Each service runs
`/bin/sh -c "npm install\nnpm start\n"`; the YAML `|` block adds a trailing
newline, so BusyBox `sh` remains PID 1 instead of replacing itself with `npm`.
A shell as PID 1 without handlers ignores SIGTERM, so Node never ran its
shutdown and SimplyStore's lock was not released. A throwaway container with
the same image and entrypoint reproduced it: without the trailing newline Node
received SIGTERM and exited 0 immediately; with it, nothing reached Node and
the container exited 137 after 10 s.

Requested change to `docker-compose.yml`:

- run `exec npm start` in all four services, so npm becomes PID 1 regardless
  of the trailing newline and forwards SIGTERM;
- give `curriculum-store` `stop_grace_period: 30s`, because a running slow
  query (up to its 10 s limit) delays SimplyStore's close past Docker's default
  10 s.

The maintainer's uncommitted edits to the same file (Node 24 for
`curriculum-store`, required by SimplyStore 0.11, and removal of the obsolete
`version` key) are included in this change.

Evaluation criteria: one Ctrl-C / `docker compose stop` stops every service
with exit 0 well within its grace period, Node receives SIGTERM, and
curriculum-store's lock directory is gone afterwards.

Out of scope: automatic recovery after real crashes (discussed as SimplyStore
self-healing and deferred), SimplyStore's short startup window in which a stop
still leaves the lock, the existing stale lock in the local dataset, and the
curriculum-store submodule pin.

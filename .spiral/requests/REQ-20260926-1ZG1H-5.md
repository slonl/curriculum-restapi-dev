# Stop Docker services cleanly

Maintainer report and instruction, 2026-09-26. After testing SimplyStore 0.11.1
in `curriculum-store`, the store lock remained after shutdown. The maintainer:
"I pressed ctrl-c once in the docker compose process, which should have started
normal shutdown", with no queries in flight. After the investigation below the
maintainer instructed: "Please make those changes".

Evidence from Docker's event log for that run: every service received SIGTERM
and was killed with SIGKILL exactly 10 s later (exit 137). Each service runs
`/bin/sh -c "npm install\nnpm start\n"`; the YAML `|` block adds a trailing
newline, so BusyBox `sh` remains PID 1 instead of replacing itself with `npm`.
A shell as PID 1 without handlers ignores SIGTERM, so Node never ran its
shutdown and SimplyStore's lock was not released. A throwaway container with
the same image and entrypoint reproduced it: without the trailing newline Node
received SIGTERM and exited 0 immediately; with it, nothing reached Node and
the container exited 137 after 10 s.

Requested change to `docker-compose.yml`:

- run `exec npm start` in all four services, so npm becomes PID 1 regardless
  of the trailing newline and forwards SIGTERM;
- give `curriculum-store` `stop_grace_period: 30s`, because a running slow
  query (up to its 10 s limit) delays SimplyStore's close past Docker's default
  10 s.

The maintainer's uncommitted edits to the same file (Node 24 for
`curriculum-store`, required by SimplyStore 0.11, and removal of the obsolete
`version` key) are included in this change.

Original evaluation criteria: one Ctrl-C / `docker compose stop` stops every
service with exit 0 well within its grace period, Node receives SIGTERM, and
curriculum-store's lock directory is gone afterwards.

The original request left automatic recovery after real crashes, SimplyStore's
short startup window, the existing stale lock in the local dataset, and the
curriculum-store submodule pin out of scope.

## Goal extension

After the shutdown change was evaluated, the maintainer instructed: "Keep the
cycle open, I think the self healing part should be included in it." Asked how
to organize the cross-repository work, the maintainer chose a chain of cycles
and clarified: "the docker-compose and restapi-dev are only for development,
no restart needed here".

The request is therefore extended: after curriculum-store is forcibly stopped,
the next `docker compose up` must start it without manual lock removal when
SimplyStore can prove that the previous lock owner is dead. The implementation
is supplied by a released SimplyStore version through curriculum-store; this
repository updates its curriculum-store submodule pin and verifies the complete
path with a SIGKILL followed by a new `up`.

Extended evaluation criteria: the original graceful-shutdown criteria continue
to pass, and after curriculum-store is killed with SIGKILL, the next
`docker compose up` starts the store, an application-level request succeeds,
and no manual lock removal is needed.

No automatic restart policy is requested. A live owner, an ambiguous owner, an
unfinished command, multi-host ownership, and legacy locks that cannot be
proved dead remain protected or require explicit administrative recovery.

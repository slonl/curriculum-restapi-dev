## Initialization and verification

Empty local `data/command-log.jsontag` and
`data/command-status.jsontag` files were created. `npm run init-integrity` then
used SimplyStore 0.12.0's explicit initializer. It decoded and validated the
dataset, IDs, framing and available artifacts before atomically publishing
`data/data.integrity.jsontag`. The result reported one sealed file and no
committed commands.

The manifest records the exact base-dataset digest above. Post-initialization
SHA-256 checks confirmed that neither the tracked dataset nor schema changed.
`inspectStore` reports `ready: true`, no errors and no committed commands. Its
expected administrative warning remains: surviving files alone cannot prove
history completeness or original hidden inputs.

The generated manifest and empty logs are mutable local store state. Store
commit `9fd59b6` adds `data.integrity.jsontag` to the same ignore policy already
used for the command and status logs, leaving the child and parent worktrees
clean while retaining the initialized files locally.

## Failed optional live-start probe

An optional startup probe loaded the sealed store successfully but the sandbox
denied binding an HTTP listener with `EPERM`. The process exited without
accepting a command and retained its ownership lock, as designed for an
uncertain startup outcome. The process and host identity were checked, then
SimplyStore's audited `recover.mjs unlock --confirmed-stopped` flow preserved
the owner diagnostics in `/tmp/curriculum-store-unlock-audit.json` and released
the lock. A subsequent sealed-store inspection again reported ready with no
errors, and no lock remains.

## Parent integration

The corrected parent pin and cycle record passed prospective-tree Spiral RDF

## Limits

The integrity manifest certifies the current local bytes from this point
forward; it cannot reconstruct absent historical provenance. The HTTP startup

sealed-store inspection used by startup completed successfully before and after
the audited lock release.

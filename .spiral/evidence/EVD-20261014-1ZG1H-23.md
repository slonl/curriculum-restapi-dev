# Single-object audit trail verification

Observed on 2026-10-14 for parent implementation commit `142236e`, which pins
curriculum-store `f7a323d` and curriculum-rest-api `5d64ba3` on
`spiral/CYC-20261014-1ZG1H-22-object-audit-trail`.

## Store adoption and history behavior

The embedded curriculum-store manifest and lockfile resolve
`@muze-nl/simplystore` 0.12.0. Its real-process fixture converts a
curriculum-shaped dataset, applies two successful commands with different
authors and messages to one object, and queries history through
`meta.history.get(meta.index.id.get('/uuid/root'))`.

The fixture proves:

- the base, first change and second change appear oldest first as versions 0,
  1 and 2;
- the immutable titles are `original`, `updated` and `current`;
- each entry has an ISO dataset-file timestamp and command timestamps equal the
  corresponding entry timestamp;
- command ID, name, author, message and version are exposed while original
  command input is absent; and
- the same history and metadata are returned after stopping and restarting the
  store.

`npx tap --disable-coverage --node-arg=--no-node-snapshot test/*.mjs` passed all
84 assertions. `npm ls @muze-nl/simplystore --depth=0` reports 0.12.0.

## REST and browser behavior

The REST query begins with the current indexed record and passes that object to
`meta.history.get`. It uses `/query/`, returns `null` for an unknown current ID,
and projects only version, timestamp, compact command metadata and the
historical object.

The authenticated `GET /uuid/:id/history` integration fixture proves reader
access without an editor grant, anonymous rejection before store access,
`application/jsontag` success, `Cache-Control: no-store` on success and error
paths, 404 for an unknown UUID and the existing bounded 500 response for a
store failure. A historical object's JSONTag class and shared-link identity
survive the store and REST round trip.

The browser fixture proves that the ordinary item gets a `Geschiedenis` link,
the dedicated route loads the JSONTag resource, identifies the current object,
labels the base version, renders command author/message metadata and produces
an expandable raw snapshot. Loading, empty and failure states are visible, and
clearing the view invalidates a pending request so its late result cannot
replace later navigation.

`npx tap --disable-coverage test/history.mjs test/orphans.mjs` passed 101/101,
including the existing orphan regression suite. `npm run lint` completed
successfully. The focused history file alone passed 50/50.

## Visible baseline limitations

The store's default `npm test` runs all 84 assertions successfully, then exits
nonzero because Tap applies the repository's existing coverage threshold to
68.06% statement coverage. Its existing `npm run lint` also exits nonzero
because the repository has no ESLint configuration file. These limitations
were already documented in earlier store evidence and this cycle does not alter
the tooling configuration.

The full REST `npm test` reports 106 passing and three failing assertions, all
in the pre-existing `test/changes.mjs`. That test expects `new Changes(array)`
to hydrate its argument, while the unchanged constructor ignores a supplied
array. `git diff 3f58316..5d64ba3 -- test/changes.mjs
www/assets/js/changes.mjs` is empty, and blame dates the behavior to 2025. The
cycle neither caused nor repairs that unrelated mismatch; focused current and
regression suites are green.

## Limits

Verification uses a compact store fixture and a fake-store REST boundary; it
does not start the complete development stack or use maintainer data. The UI is
exercised through its route/action model and template contract rather than a
pixel-level browser test. Property diffs, restore, command-wide history,
same-version peers, original inputs and whole-dataset historical switching are
not implemented by design.

# Verification Evidence: FO Deprecated Replacement Probe

## Claim Being Verified

A limited FO-only search can find deprecated entities with no `replacedBy` and
produce suitable human-review candidate replacements using active FO data plus
Git history timing.

## Why This Evidence Exists

Cycle 3 narrows the semantic-continuity question to lower-drift FO entities:
deprecated FO rows without `replacedBy`, where likely successors may have been
introduced around the same time as the old entity was deprecated.

### Ambiguous candidates

Many exact text matches are still ambiguous because FO repeats the same
doelzin text across multiple active contexts.

Example: deprecated `bb4827ad-68d7-4856-8845-763bb7b5dc11` (`Doelzin 1A`,
"De school zorgt voor een rijke taal- en leesomgeving.") has five active exact
matches across `Functionele kerndoelen Nederlands` and `Kerndoelen Nederlands`.
The active candidates already replace different IDs. Without the old entity's
full graph/set context, this should be a context-filtering task, not a direct
candidate.

This ambiguity is the main reason the aggregate `1,084` exact candidate pairs
should not be read as 1,084 likely links.

## Result

The limited FO-only probe is positive for a maintainer review workflow:

- There are real deprecated FO entities with no `replacedBy` where the active
  successor candidate can be found cheaply.
- Git history materially improves trust: same-commit active-to-deprecated
  movement plus candidate introduction is much stronger than text similarity
  alone.
- The most useful first queue is exact same-type/title/description matches with
  a single active candidate and same-release timing.

The probe remains negative for unattended data mutation:

- Duplicate labels produce many false or ambiguous candidate pairs.
- Some plausible successors already `replace` other IDs but omit the old ID;
  this could be an intentional modelling choice or an omission.
- Set-level version replacements can be semantically plausible even when Git
  timing is not close enough to trust automatically.

## Failure Cases / Limits

This pass used exact text matching, not a full semantic model. It likely misses
renamed, split, merged, broadened, narrowed, or reparented successors.

Deprecated parent context was incomplete for some old rows, so active graph
context could not always be compared symmetrically.

Git history was checked for a selected sample, not all 58 single-candidate
groups. The aggregate counts identify a promising review queue but do not prove
every queue item is good.

## Evidence Quality

This is decision-quality evidence for whether a limited FO deprecated-entity
review queue is worth further exploration. It is not production acceptance
evidence for adding any specific `replacedBy` / `replaces` links.

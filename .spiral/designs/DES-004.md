# Design: FO Continuity Review Queue Probe

## Role

Defines a read-only Cycle 3 probe script for producing a bounded FO continuity
review queue with textual similarity, graph context, existing link clues, and
Git timing evidence.

## Why This Exists

`EVD-009` showed that non-exact matching improves recall but becomes ambiguous
without graph context, programme/level information, existing `replaces` clues,
and Git timing. The maintainer asked to enhance the probe with those inputs.

## Cultural Influence / Constraints

Continuity links preserve durable third-party references. The design favors
auditable review evidence and explicit ambiguity over automatic mutation.

## Behavior / Responsibilities

The probe should:

- read FO active and deprecated JSON from a local FO checkout;
- bound the default search to the Nederlands family excluding Nederlandse
  gebarentaal;
- identify deprecated descendants with missing/empty `replacedBy`;
- rank active same-type candidates;
- explain each candidate with text, graph, link, and timing scores;
- show old and candidate graph context in the review output;
- warn when graph context suggests a candidate belongs to a different
  programme or level family;
- allow focused review with type filters and generic-row exclusion;
- write only to stdout and never mutate FO data.

## Boundaries

What belongs here:

- a probe/review-queue script under `.spiral/tools/`;
- scoring and explanation sufficient for Cycle 3 evidence;
- command-line controls for bounded review.

What must remain outside:

- production `replacedBy` / `replaces` edits;
- a maintainer-workspace UI;
- a permanent semantic matching service;
- unattended acceptance thresholds.

What change should this boundary protect us from:

- mistaking a useful candidate ranking for accepted domain truth.

## Supporting / Intrinsic Work

| Support | Why necessary |
|---|---|
| Parent indexes | Graph context must be fast enough to use interactively |
| Two-stage Git enrichment | `git log -S` is slow, so timing should enrich top candidates rather than every possible pair |
| Type and generic filters | `fo_uitwerking` / `fo_illustratie` rows can flood output with repeated generic titles |

## Alternatives Considered

| Alternative | Why Not Now | Evidence / Trade-Off |
|---|---|---|
| All-entity Git timing | Too slow for this repository | A top-16 Git enrichment run took about a minute |
| Exact text only | Misses typo cleanup and title/prefix/wording changes | `EVD-009` found useful non-exact examples |
| Embeddings or model calls | Adds dependencies and model variance before graph/timing basics are proven | Current cycle can still learn from deterministic scoring |

## Complexity / Maintainability Check

- Concepts introduced: text score, graph score, link score, timing score,
  context warning, focused filters.
- Dependencies introduced: none beyond Node.js and local Git.
- Expected change radius: `.spiral/tools/` and Cycle 3 evidence only.
- Replaceability considerations: the script is a probe and can be replaced by a
  future production implementation.
- What would make this harder for a future agent/human to change: treating the
  scoring numbers as calibrated probabilities.

## Verification Plan

The probe is useful if it can:

- run without Git timing for a quick deterministic queue;
- run with bounded Git timing enrichment for focused review;
- surface graph context and context warnings in the output;
- keep generic child rows from hiding higher-level review items when requested;
- leave FO data unchanged.

## Deferred Decisions

- Whether embeddings or LLM-based semantic scoring add value after graph/timing
  ranking.
- Whether this should become a maintainer-workspace feature.
- How a domain reviewer should accept/reject candidate links.

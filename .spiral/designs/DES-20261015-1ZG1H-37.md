# Design: layered, isolated development verification

## Design intent

`curriculum-restapi-dev` exposes one verification entry point with two layers:

1. deterministic component checks that are useful on every change; and
2. a slower Compose smoke exercise that verifies the actual service boundaries
   against a disposable copy of the tracked curriculum data.

The layers share one success result but remain individually invokable so a
developer can get quick feedback without disguising the integrated check.

## Component-test semantics

REST and Store keep coverage collection enabled in their default test commands,
but use Tap's `allow-incomplete-coverage` behavior so assertion failures and
runtime failures determine `npm test` success. This avoids Tap's `disable`
mode, which the local probe showed can obscure child execution in the sandbox.

Each child also exposes a separate coverage target check with an explicit 90%
target for statements, branches, functions, and lines. The target check is
allowed to fail while the measured gap remains; that failure is reported as a
coverage target gap, not as a behavioral regression. This avoids silently
normalizing today's lower numbers as the desired standard.

The ordinary verification path records the coverage summary without enforcing
the target. Cheap, discriminating tests may improve coverage in this cycle, but
closing REST's particularly large function gap or Store's statement/line gap
must not expand the cycle into broad test-suite construction.

The parent fast layer runs child tests, REST lint, and Compose configuration.
Store lint is reported as unavailable rather than silently repaired because the
known missing ESLint flat configuration is outside this cycle.

## Compose isolation

The normal Compose definition remains the source of service topology. Small
configuration seams make its mutable boundaries selectable:

- host ports and container names are parameterized;
- Store data can be over-mounted from a temporary directory;
- REST credentials can be over-mounted from temporary files; and
- dependency installs write to project-scoped `node_modules` volumes and use
  lockfiles where available rather than modifying source directories.

The smoke runner creates a unique temporary directory and Compose project. It
copies only the tracked Store baseline (`data.jsontag` and `schema.jsontag`),
creates a fresh integrity baseline, writes dedicated editor credentials, and
uses isolated host ports/container names. A cleanup trap runs `docker compose
down --volumes` only for that project. It never calls `docker-clean.sh`.

## Observable smoke path

The runner:

1. snapshots parent and child Git status;
2. starts all four services and waits for their public readiness boundaries;
3. verifies authenticated REST object and Search reads;
4. verifies Registration rejects a malformed request without mutating keys;
5. updates a known tracked object title through the authenticated REST command
   endpoint and polls through non-terminal states;
6. verifies the new object value and history metadata;
7. restarts Curriculum Store and verifies the value and history again;
8. shuts down its project and compares Git status with the starting snapshot.

The command uses the tracked object only inside the temporary Store copy. A
missing object or changed contract is a useful smoke failure rather than a
reason to mutate the development data to satisfy the script.

## Failure behavior

Every subprocess is checked. Readiness and polling have deadlines. On failure,
the runner prints the temporary path and Compose logs before bounded cleanup.
Temporary state is removed after success and retained after failure for
inspection.

## Alternatives rejected

| Alternative | Reason |
|---|---|
| Run Compose against the working Store data and restore afterward | A failed process could leave commands, indexes, locks, or integrity changes behind |
| Duplicate the full topology in a second Compose file | The smoke definition would drift from the development environment it claims to verify |
| Disable coverage entirely | Loses useful measurement and behaved poorly in the first local Tap probe |
| Set target thresholds to today's rounded-down values | Converts the current accident into policy and loses the maintainer's 90% direction |
| Keep implicit 100% coverage as `npm test` | Continues to mislabel 127/127 and 84/84 behavioral results as test failures |
| Exercise only REST and Store | Registration and Search would remain untested in the authoritative integrated environment |

## Deferred work

Broad work required to reach 90%, Store lint configuration, complete
Registration/Search suites, browser automation, import/export verification,
image caching, and hosted CI remain separate decisions.

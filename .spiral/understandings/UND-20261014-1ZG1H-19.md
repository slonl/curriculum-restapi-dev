# Understanding: one-object history as a usable audit trail

## Interpretation

The desired outcome is a narrow read-only audit trail reached from an existing
curriculum object view. Given the object's current UUID, a reader can see every
stored version of that record in chronological order, who submitted the
successful command, when its dataset file was written, and the submitted commit
message. Each entry also makes the complete historical object inspectable.

This is not a general command-log browser. It begins with one current object and
uses that object's SimplyStore history. The dependency update is supporting
work, not the cycle's product goal.

## Current effective behavior

- The embedded `curriculum-store` clean `main` tip depends on
  `@muze-nl/simplystore` `^0.11.2`; its lockfile resolves 0.11.2.
- SimplyStore 0.12.0 now exposes successful command metadata and immutable
  per-object history through `meta.history`.
- `curriculum-rest-api` exposes the current object at `/uuid/:id`, but has no
  audit/history endpoint.
- The browser routes `/uuid/:id` to the existing item view and has no history
  link or audit template.
- The parent currently pins curriculum-store `b2f55cb` and REST API `3f58316`.

## Evidenced gap

The released history capability cannot be used from the integrated curriculum
environment: the store is pinned before 0.12.0, the REST layer does not query
`meta.history`, and the object view offers no path to an audit trail.

## Material assumptions

- `/uuid/:id/history` is the REST resource and `/uuid/:id/history/` is the
  browser route.
- History resolution starts from the current indexed object, allowing its
  record history to include ID removal/restoration where SimplyStore retained
  ownership; an unknown current object returns 404.
- The API keeps SimplyStore's oldest-first order and includes the base entry.
- Existing API authentication is sufficient; history gets no separate editor
  authorization.
- A minimal UI lists metadata and an expandable raw object snapshot. It does
  not attempt schema-aware historical rendering or property diffs.
- Standard query timeout, memory and result-size limits bound unusually large
  histories; this first version has no pagination.

## Scope boundary

Included are the two embedded application repositories and their parent pins.
Excluded are the separate standalone checkout, IndexedDB work, frontend
modernization, restore/edit actions, command-wide audit, same-version peers,
original command inputs and complete historical dataset switching.

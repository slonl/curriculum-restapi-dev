# Understanding: FO Deprecated Replacement Probe

## Interpretation

The maintainer wants a narrowly scoped semantic-continuity test inside FO rather
than another broad FO-vs-LDK comparison. The target population is entities in
`curriculum-fo/data/deprecated.json` whose `replacedBy` field is missing or
empty.

The experiment should identify plausible active FO replacement candidates and
use Git history as evidence, especially commit timing around when an old entity
entered `deprecated.json` and when a similar new entity appeared or changed.

## Important Constraints

- Do not mutate production data.
- Do not add `replacedBy` links in this cycle.
- Treat candidates as suggestions for human review.
- Use Git history as supporting evidence, not as proof of semantic continuity.
- Prefer a small, inspectable sample over a whole-dataset migration.

## Material Assumptions

The likely useful signal is a combination of:

- entity title/description similarity;
- matching or nearby prefixes;
- graph neighborhood where recoverable;
- temporal proximity in Git history;
- same file/type family where recoverable from deprecated entity shape.

## Uncertainty

Some deprecated entities may intentionally have no replacement. Some may be
delete-only placeholders. Git history may be noisy if large generated updates
move many entities at once.

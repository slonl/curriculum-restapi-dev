# Understanding: stale constructor-based test setup

## Intended outcome

The repository's documented `npm test` command should pass, and correcting it
must not hide a defect in the change-history behavior used by the browser.

## Current effective behavior

An unrestricted run of `npm test` executes 127 assertions: 124 pass and three
fail in the two oldest cases in `test/changes.mjs`. Both failing cases construct
`new Changes(array)` and expect the array to be hydrated.

Git history shows that the tests were introduced in 2024. Commit `5bb928b`
changed `Changes` to restore and append a newline-delimited log in February
2025 and removed array hydration from the constructor without updating these
tests. Current production call sites create an empty/restored `Changes`
instance and append `Change` objects with `push`; none passes an array to the
constructor. Newer orphan-deletion tests already use that incremental form.

## Evidenced gap

The default test command remains red because two legacy test setups exercise a
removed construction form. This obscures meaningful regressions even though
the production append-and-merge path is not implicated by the failures.

## Material assumptions and falsification

Treat array construction as stale test setup, not a supported API to restore.
Rewrite only those setups to append hydrated `Change` instances. The existing
length and merged-property assertions must then pass unchanged. If they do not,
or if another suite fails, the stale-test explanation is falsified and the
production implementation needs separate correction.
